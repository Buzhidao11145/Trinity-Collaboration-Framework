# 实战案例：参数名陷阱

> **本文件已脱敏处理。** 特定平台名称和项目信息已移除。
>
> **用途：** 展示决策规则从实战中诞生的完整过程
> **所属：** Trinity 框架实战案例

---

## 背景

在研究某电商平台的搜索 API 时，团队使用参数名 `keyword` 调用 API，返回的是推荐流而非真实搜索结果。API 返回 HTTP 200，数据格式也符合预期，但内容完全不对。

## 误判

团队立即定性为"此 API 不是真实搜索接口"。随后花了大量时间从多个方向寻找替代方案：

| 方向 | 投入时间 | 结果 |
|:-----|:--------:|:-----|
| 协议层分析（逆向客户端网络库） | 6 小时 | 无进展 |
| 页面渲染流程逆向 | 4 小时 | 无进展 |
| 请求拦截与参数枚举 | 3 小时 | 无进展 |
| **总计** | **13 小时** | **全部落空** |

没有一个人在第一时间怀疑参数名本身有问题。所有人的默认假设都是：**参数名是对的，接口是错的。**

## 转折

规划者介入后，基于决策知识库中的"参数名排查清单"提出质疑——**先换参数名再试。**

清单上已经列出了 10 个备选参数名（`q`、`query`、`keyword`、`search`、`text`、`wd`、`searchId`、`id`、`keywordSearch`、`input`），这是之前同类错误的教训提炼。

换用参数名 `q` 后，API 立即返回了真实搜索结果。

## 结果

- API 一直可用，从未出过问题
- 问题是参数名与文档标注的不一致
- 13 小时的攻坚，被 1 个参数名替换解决
- 该规则被正式写入决策知识库，成为后续所有 API 研究的第一优先级检查项

## 教训提炼

### 核心教训

当 API 返回"看起来正常但不符合预期"的数据时，**先换参数名再试。**

### 为什么会发生

| 因素 | 说明 |
|:-----|:------|
| **确认偏误** | 团队默认参数名是正确的，所有证据都在往"接口不对"的方向解释 |
| **经验盲区** | 之前的 API 经验中，参数名与文档总是一致，没有遇到过参数名不同的情况 |
| **缺乏检查清单** | 没有标准化的排查流程，每个人按直觉找方向 |

### 决策规则的转化

该案例被直接转化为决策规则 #1（参数名排查清单）：

- **触发条件**：API 返回"看起来正常但不符合预期"的数据
- **决策建议**：先换参数名再试，备选清单含 10 个常见参数名
- **严重程度**：🔴 高 — 曾导致六轮攻坚白费

---

## Trinity 的价值

在没有框架之前，这个错误导致了一整天的攻坚白费。有了框架之后，规划者在复盘时自动触发参数名排查流程：

```
API返回异常 → 检查参数名清单 → 依次测试备选参数名 → 找到正确的参数名
→ 更新决策规则（如果清单中没有该参数名） → 继续任务
```

**同类错误不再发生。**

---

## 延伸思考

这个案例揭示了 Trinity 框架的一个核心机制：**知识复利**。

一次错误是一个点教训，但结构化为决策规则后，它变成了一个可复用的检查点。下一次遇到类似问题时，规划者不需要重新"发现"这个教训——规则已经在那里了。

这就像一个团队中有了一个"不犯同样错误"的成员。Trinity 中的规划者和执行者，通过决策知识库的支持，正是这样的成员。
