## 使用说明

- 每条规则包含：触发条件、决策建议、来源说明（已脱敏）、验证状态、严重程度
- 新规则必须标注来源背景，禁止写入未经实战验证的推测
- 规则状态：🟢 已验证 / 🟡 部分验证 / 🔴 待验证
- 严重程度：🔴 高（曾导致重大失败）/ 🟡 中（可节省大量时间）/ 🟢 低（锦上添花）

## 规则 1：参数名排查清单

| 字段 | 内容 |
|------|------|
| **触发条件** | API 返回"看起来正常但不符合预期"的数据 |
| **决策建议** | 先换参数名再试。备选清单：`q`、`query`、`keyword`、`key`、`search`、`text`、`wd`、`searchId`、`id`、`keywordSearch`、`input` |
| **来源说明** | API研究中后端实际接受的参数名与文档/前端JS中标注的不一致，导致多轮攻坚返回空结果 |
| **验证状态** | 🟢 已验证 — 参数名替换后API立即返回正确数据 |
| **严重程度** | 🔴 高 — 曾导致多次无效攻坚 |

**延伸教训：** 遇到API行为异常时，不要死磕参数值，先怀疑参数名。用浏览器的Network面板或抓包工具确认真实请求。

## 规则 2：原版文件确认

| 字段 | 内容 |
|------|------|
| **触发条件** | 修改任何文件前 |
| **决策建议** | 必须先确认原版文件是否正确：检查大小（`ls -lh`）、检查类型（`file` 命令）、检查能否正常打开/解压 |
| **来源说明** | 多次使用已修改过的版本作为"原版"，导致重复操作 |
| **验证状态** | 🟢 已验证 — 确认原版后再操作，一次成功 |
| **严重程度** | 🔴 高 — 曾导致多次无效操作 |

**操作模板：**
```bash
# 前置检查三部曲
ls -lh original.file               # 检查大小（与已知值比对）
file original.file                  # 检查文件类型
ditto -x -k original.file /tmp/v   # 检查能否正常解压（适用于IPA）
```

## 规则 3：代理模式优先

| 字段 | 内容 |
|------|------|
| **触发条件** | 面对采用签名+时间戳+设备指纹验证架构的App |
| **决策建议** | 优先寻找代理模式的方法而非逆向签名算法。代理模式下，App 自身的网络库会代为处理签名，无需逆向安全SDK |
| **来源说明** | API研究经验。空值方案绕过匿名API成功，但签名算法逆向耗时巨大且路径不稳定 |
| **验证状态** | 🟡 部分验证 — 匿名API已验证通过，认证API仍需手动登录捕获会话 |
| **严重程度** | 🟡 中 — 可节省大量逆向时间，但不是万能方案 |

## 规则 4：空值验证优先

| 字段 | 内容 |
|------|------|
| **触发条件** | 遇到新参数（尤其是安全/签名类参数） |
| **决策建议** | 先用空值测试必要性：传空字符串、0、false、null 各试一次。如果空值能通过验证，说明该参数不是强制校验的，无需投入精力逆向 |
| **来源说明** | 安全参数研究中发现空值绕过验证成功，说明该字段不是签名算法的必要组成部分 |
| **验证状态** | 🟢 已验证 — 空值绕过在多个场景下被验证有效 |
| **严重程度** | 🟡 中 — 避免不必要的逆向投入 |

**测试清单：**
```python
# 每次遇到新参数，按顺序测试以下值
test_values = ["", "0", "false", "null", "test", None]
for val in test_values:
    if try_request(param=val).status_code == 200:
        print(f"参数可绕过: {val}")
```

## 规则 5：ditto 解压打包

| 字段 | 内容 |
|------|------|
| **触发条件** | 处理 IPA 文件（解压或打包） |
| **决策建议** | **全程用 ditto，禁用 Finder 和简易压缩命令。** 解压用 `ditto -x -k`，打包用 `ditto -c -k`。禁止使用：Finder 双击解压、`unzip` 解压、`zip` 打包 |
| **来源说明** | IPA修改中文件变小问题。使用 Finder 解压再压缩后 IPA 文件大幅缩小，App 无法正常安装 |
| **验证状态** | 🟢 已验证 — ditto 操作后文件大小正常，App 正常安装运行 |
| **严重程度** | 🔴 高 — 文件损坏会导致所有后续操作无效 |

## 规则 6：硬约束比软请求更有效

| 字段 | 内容 |
|------|------|
| **触发条件** | 需要约束AI执行行为时 |
| **决策建议** | 使用自检清单、强制验证点、固定步骤模板等**硬约束**，而非提示词中的"请不要"。硬约束嵌入操作流程中，执行者每次操作都会经过，不易忽略 |
| **来源说明** | 框架核心原则迭代教训。用户发现"请不要调全量API"的软约束经常被忽略，改成"列出API URL→等待确认→再执行"三步硬约束后，违规率大幅下降 |
| **验证状态** | 🟢 已验证 — 多轮任务执行中反复验证 |
| **严重程度** | 🟡 中 — 影响所有任务执行的可靠性 |

**硬约束实现示例：**
```markdown
## 执行前自检清单（内嵌到流程中）
☐ 我已列出即将调用的API URL？
☐ 我已等待决策者确认？
☐ 我的回退方案是什么？
☐ 这个操作在授权范围内？

任意一项为"否" → 暂停执行
```

| **验证状态** | 🟢 已验证 |

## 规则 8：二进制版本匹配

| 字段 | 内容 |
|------|------|
| **触发条件** | 从内存 dump 获取脱壳二进制用于构建时 |
| **决策建议** | 内存 dump 必须来自与目标 IPA **完全相同的二进制版本**（检查 ncmds/load commands 数量一致）。版本不匹配时注入动态库会导致闪退 |
| **来源说明** | 二进制版本不匹配导致注入失败。内存 dump 与 IPA 二进制 ncmds 数量不一致 |
| **验证状态** | 🟢 已验证 |
| **严重程度** | 🔴 高 — 版本不匹配所有注入操作无效 |

**验证命令：**
```bash
otool -l /path/to/binary | head -5  # 查看 ncmds 和 sizeofcmds
# ncmds 必须一致，sizeofcmds 允许差 0x40（一个 LC_LOAD_DYLIB 的大小）
```

| **验证状态** | 🟢 已验证 |
| **严重程度** | 🔴 高 — 发现高危漏洞时的应对方式决定了整个测试的合法性和安全性 |

## 规则 10：静态分析优先

| 字段 | 内容 |
|------|------|
| **触发条件** | 面对任何可疑文件、未知样本或新目标时 |
| **决策建议** | 先用静态分析工具收集基本信息，确认需要动态分析后再搭建隔离环境。标准静态分析五步：`file` → `strings` → `nm` → `otool -L` → `codesign -dvv` |
| **来源说明** | 多个逆向项目中跳过静态分析直接运行动态Hook导致SIGKILL |
| **验证状态** | 🟢 已验证 — 实战验证通过 |
| **严重程度** | 🟡 中 — 影响分析效率和方法选择 |

**操作模板：**
```bash
# 标准静态分析五步（按顺序）
file target                    # 1. 文件类型识别
strings target | head -50      # 2. 关键字符串提取
nm -gU target                  # 3. 外部符号
codesign -dvv target 2>&1      # 4. 代码签名/entitlements
otool -L target                # 5. 链接库依赖
# 完成以上五步后再决定是否进入动态分析
```

## 规则 12：批量分析工具 — 逐阶段try-catch

| 字段 | 内容 |
|------|------|
| **触发条件** | 运行批量分析脚本（如iOS App批量逆向）|
| **决策建议** | 每个分析循环内按阶段独立try-catch，而非一次性包裹整个流程。每个阶段捕获到异常时记录阶段编号+错误类型+堆栈。连续多个App失败时暂停并诊断设备连接状态。 |
| **来源说明** | 批量分析中多个失败项目完全没有失败原因记录。分析脚本的设计缺陷导致事后无法回溯错误。 |
| **验证状态** | 🟡 来自失败经验提炼，尚未在实战中验证修复后的方案 |
| **严重程度** | 🟡 中 — 影响批量分析的数据可用性 |

## 规则 13：硬编码凭证排查

| 字段 | 内容 |
|------|------|
| **触发条件** | 进行任何安全审计或代码审查时 |
| **决策建议** | 第一优先级搜索代码中的硬编码密钥、密码、Token、证书等凭证。搜索关键词包括但不限于：`secret`、`key`、`password`、`token`、`jwt`、`private`、`api_key`。确认后再检查：1) 算法是否对称（HS256=对称→密钥泄露=全线崩溃）；2) 角色权限是否有RBAC隔离；3) 是否有日志记录了凭证调用情况 |
| **来源说明** | 安全审计中发现 JWT 签名密钥在多份文件中找到。对称算法导致可伪造任意管理员身份。 |
| **验证状态** | 🟢 已验证 — JWT伪造已在测试环境中验证通过 |
| **严重程度** | 🔴 高 — 硬编码凭证一旦发现，通常是最高级别的安全漏洞 |

**操作模板：**
```bash
# 硬编码凭证扫描（优先级别）
grep -r "secret\|key\|password\|token\|jwt\|private\|api_key" --include="*.py" --include="*.js" --include="*.json" --include="*.md" ./target/
```

## 规则 11：注入方案选择矩阵

| 字段 | 内容 |
|------|------|
| **触发条件** | 需要向目标App注入调试/分析工具但不确定使用哪种方案时 |
| **决策建议** | 从最简单的方案开始，确认失败后升级：<br>1. **标准attach** → 如果App无反调试且运行环境不拦截。<br>2. **运行时attach**（手动打开App后连接）→ 如果启动注入被拦截但有存活窗口期。<br>3. **Gadget编译进应用包** → 如果以上均失败。 |
| **来源说明** | 多个App注入实战。三种不同类型的App需要三种完全不同的注入方案。 |
| **验证状态** | 🟢 已验证 — 三个案例全部实战验证 |
| **严重程度** | 🟡 中 — 选择错误的方法会浪费大量时间 |

**决策树：**
```
能直接注入? ──✅──→ 标准attach
  │
  ❌
  ↓
手动打开后注入能存活? ──✅──→ 运行时attach（窗口期内操作）
  │
  ❌
  ↓
Gadget编译进应用包（唯一可行方案）
```
